# Capture and replay

Tests replay recorded I/O by default: a test with a recording in `replays/` runs without helper, SSH, agents or real time. A test without one runs live, and live runs of passed tests can be recorded into `replays/` after the checks below. Release builds and archives contain no capture or replay code (Swift `DEBUG`, Rust `capture` feature).

**What is recorded.**

- The **app journal**: everything the app exchanges with the outside world in one test: helper connections (bytes both ways), terminal ptys, commands it runs, files it reads and writes, what it observes (process state, file existence, the time), its own waits (`System.sleep`) and the test's steps.
- One **helper capture** per helper process the test started: its startup facts, every I/O request and its result, its end (return status, handoff or signal). Helpers on SSH hosts (the Mac's own test sshd, the Linux test host) write theirs there; each test collects them when it ends.
- Both use one format: zstd around length-prefixed frames of binary values (`helper/core/src/system/capture/trace.rs`). Bytes stay bytes. Live captures are zstd level 1; the corpus keeps them at level 9 with `--long=27` (`.rpl.zst` either way: `Vendor/Zstd/PROVENANCE.md`), whose 128 MiB window stores a payload recorded again and again (the helper binary the bootstrap tests upload) once. `zstd -dc --long=27` expands either.
- Captures hold unredacted I/O, and the corpus is public: `--capture` stores only scrubbed copies, and the corpus's pre-push hook refuses a capture holding this Mac's private values ([scrubbing](#scrub-captures-before-sharing-them)).

**The corpus**: `replays/<TestFile>/<testName>/<key>.rpl.zst`.

- `<TestFile>` is the Swift file declaring the test class, `<testName>` the test method. A test's directory holds its app journal and all its helper captures (local and remote).
- `<key>` is a hash of what replay sees (records without the bookkeeping clock or wire version), so the same content is one file. A scrubbed corpus has random names instead; nothing reads a key from a name.
- One app journal per test: a recording names its run's pids, seeds and temp paths, so without deduplication every live re-run would look like a new variant. `store` skips a test that already has one.
- The corpus is a git submodule at `replays/` (`scripts/split-replays.py` made it one) whose path never changes: recordings name `/tmp/dt-journal/checkout/replays`. Get it with `git clone --recurse-submodules` or `git submodule update --init replays`; without it `test/xcode.py` runs only `--live` and the Debug build skips its corpus check with a warning. Changed recordings (`--capture`, `capture prune`, a deleted test directory) are changes in the submodule: commit and push there first, then stage the new `replays` commit here with the change that made them. Never push a checkout's commit before the corpus commit it names.

## Common tasks

Replaying every recording takes about 15 minutes, one class seconds. Run live only what you changed on purpose, record it, and replay the rest.

**Recording everything again is the last resort**, for when no recording can replay at all (a new wire version, below). After any change, yours or merged, replay the corpus first: the replays that fail are exactly what changed. Read each failure, then record again only those tests, and only once you know why each one changed. A fresh recording passes by construction, so recording everything hides exactly what the replay would have shown. When the recording format itself changes, or only the text of what the app sends, migrate the recordings ([Migrations](#migrations)) instead of recording them again.

**Prefer changes that touch few recordings.** A change to what many tests do (a startup request every test sends, a timer every test runs, common helper behavior) changes many recordings, each to be checked and recorded again, and recordings that passed are what tells us the rest still works. Look for a narrower change; when the wide one is needed, make it on its own, not mixed with other work.

- **I work on the app only.** Replay: `python3 test/xcode.py --suite exhaustive`, or one class: `python3 test/xcode.py DispatchTests/ChatTests`. Passing means the app still sends and asks exactly what was recorded, so the helper sees nothing new either. A replay that fails where you changed nothing: the app now does something else there ([Reading a failed app replay](#reading-a-failed-app-replay)). A test you changed on purpose, or a new test: delete its `replays/<TestFile>/<testName>/` (if any), then record it and replay that recording:

  ```sh
  python3 test/xcode.py --capture DispatchTests/ChatTests/testNew
  python3 test/xcode.py --replay DispatchTests/ChatTests/testNew
  ```

- **I work on the helper only.** Replay every helper capture on your helper (minutes; on Linux too; the Debug app build does the same and fails on any failure):

  ```sh
  "$HELPER" capture replay replays --completion required --output results/my-change
  ```

  Rust unit tests: `cd helper && cargo test --offline --features dispatch-helper/capture`. Passing means the helper answers every recorded request as before, so the app's recordings still hold. A capture that fails (`report.jsonl` names the record): the helper now does something else for that request. If that is the change you meant, the test that recorded it is stale: record that app test again (helper captures are only recorded through app tests, `--capture`). `"$HELPER" capture prune replays --dry-run` lists every helper capture that no longer replays.

- **I merged other changes.** Replay every recording on the merged code, app and helper. The failures list what the merged changes do differently; read each before recording it again. A failure in a test outside what the merge touched is a regression of the merge, not a stale recording.

- **I fix a bug.** Reproduce it from a recording first: a live failure recorded with `--capture` replays with `--replay` the same way every time ([a test that fails live sometimes](#a-test-that-fails-live-sometimes)). App fix: replay the test's class, then every app recording; the tests that now fail are exactly the ones whose recorded behavior the fix changed, so check each is the intended change and record those again. Helper fix: replay every helper capture; the failing captures name the tests to record again (live, `--capture`), then replay them in the app. Both: helper first, then record the affected tests and replay all app recordings.

- **I change the protocol** (the wire schema in `helper/core/src/wire`). Names and record layouts have permanent numbers, kept in `helper/core/src/wire/registry.txt`: the build appends what new code encodes (and warns to commit the file), never moves a number, and the generation id that starts every wire body stays, so recordings made before an addition still replay. What changes is only what uses the new names: a message that gained a field, and a recorded string that is now a name (it encodes as its number). Only types core encodes count (a helper's internal jobs add nothing). Never reorder or delete lines there. A breaking change (a name reused for something else, the value grammar) starts a new generation: write the old generation's dictionary (`capture dictionary test/replay-migrations/wire`) before changing anything, give `registry.txt` a new `schema` id and table, and add a `wire` migration naming it ([Migrations](#migrations)), which converts every recording. Merging two branches that both appended: keep the target branch's lines first; the other branch's recordings that use its new names are recorded again.

- **I want to know the recordings are not stale** (rare): record everything again into a fresh corpus and replay it. Tests that fail the second command are stale in a way the first run did not reveal (UI timing it decided differently): read their failure.

  ```sh
  git -C replays rm -r -q .            # start empty; the corpus repository's history keeps the old one
  python3 test/xcode.py --capture --live --suite exhaustive
  python3 test/xcode.py --replay --suite exhaustive
  ```

- **I change what the app sends** (a setup script's text, a git argument, a default that decides what it lists): `ReplayMigrationTests` fails with the fingerprint to name. Add a migration ([Migrations](#migrations)): a rewrite where every recorded answer still holds, else a rerecord of the tests whose answers changed.
- **I want to check that a test's app and helper recordings belong together**: `capture check` ([The three checks](#the-three-checks)).
- **I want to know the recordings hold no private data**: [scrubbing](#scrub-captures-before-sharing-them).
- **I write a test that replays and does not flake**: [Writing tests that replay](#writing-tests-that-replay). In short: all I/O and machine facts through `System`, waits through `TestSupport.eventually`, timers named, ids from `System.uuid()`, nothing left behind for the next test.

## Workflows

- **Run tests** (default): replay what `replays/` has, run the rest live. A test whose journal diverges fails: a missing recording means live, a wrong recording means failure. A journal of another protocol version fails its test with a hint to run `capture prune`.

  ```sh
  python3 test/xcode.py DispatchTests/ChatTests
  python3 test/xcode.py --live DispatchTests/ChatTests     # every test live, the corpus ignored
  ```

- **Record** live tests and add the passed ones to the corpus.

  ```sh
  python3 test/xcode.py --capture DispatchTests/ChatTests
  python3 test/xcode.py --capture --live DispatchTests/ChatTests   # record tests already in the corpus too
  ```

  Everything stays in `build/captures/` for debugging, failed tests included, laid out as the corpus: `<TestFile>/<testName>/` holds the test's app journal (`<uuid>.rpl.zst`), its local helper captures (`helper-<pid>-<start>.rpl.zst`) and a folder per SSH host with that host's. `cases.jsonl` has each test's start, end and outcome; `tests.json` each test class's file. The path is the same in every capture (test processes see it, and recordings hold it), so it names no run and `--capture` refuses a `build/captures` that holds an earlier capture: move that one away to keep it (and back to replay it). On an SSH host a test's helpers write into `~/.cache/dispatch-capture/<digest of its staging folder>/`, the same folder in every capture of that test; after the test its new files come over (a copied file is acknowledged there, never deleted). Files left by a capture whose collection failed come along with the next capture of that test, link to no journal, and make `store` refuse the test ("not linked"): capture it again.

  First `test/scrub.py` scrubs the run into `build/captures-scrubbed/` ([automatically](#automatic-scrub)); then `capture store` takes each passed test from there: every helper capture must replay on the current helper, and `capture check` must find its app and helper ends agreeing and linked. Only then are its files placed in `replays/`. A test that does not pass these checks stays in staging and the run reports it.

- **Verify one run** by replaying only its recordings (nothing runs live): `python3 test/xcode.py --replay DispatchTests/ChatTests`. The capture's tests go to a scratch corpus under `build/app-replay/<id>/`, failed ones included (they reproduce their failure); a selected test without a journal there fails.

- **Building checks the helper against the corpus.** A Debug build, right after building the helper, replays every helper capture in `replays/` on it. Any failure fails the build and names the captures; the results stay in `build/helper-rust/replay-results-<pid>/`. Either the change broke the helper, or the recordings no longer apply (a deliberate protocol change): then drop them.

- **Changed a test?** Its recording describes the old test, so replay fails it as a different capture. Delete `replays/<TestFile>/<testName>/`; the next `--capture` run records it again. A test's steps (its waits) are told apart by their order alone: moving code leaves its recording valid, adding or removing a wait changes it. Each step also records its source line, for reports only.

- **A fresh recording that fails its own replay** (passes live, fails replayed alone every time) caught an order replay does not reproduce: the app's reaction overtaken by a later input, or a hangup or write the app does only after work it did first in capture. Look at the frontier first ([Reading a failed app replay](#reading-a-failed-app-replay)); if the failure is the same with the original and a scrubbed copy, record it again in its class: move its directory out of `replays/` (`capture store` skips a test already in the corpus), run `--capture <run> DispatchTests/<Class>` (the class's other tests replay, this one runs live), then replay it alone a few times.

- **Drop recordings that no longer replay**, never silently. Every helper capture that fails on this helper is dropped, and so are app journals of another protocol version (the app reads only its own); the next `--capture` run records those tests again.

  ```sh
  "$HELPER" capture prune replays/ --dry-run
  "$HELPER" capture prune replays/
  ```

## The three checks

- **Helper replay** (fast, Rust): each helper capture runs the current helper against its recording. The helper runs its real event loop; the replay answers each I/O request with the recorded result and fails on any request the recording does not have next (operation, arguments, full write buffers). `--completion required` also demands that the replay end the way the recording did (return status, handoff, signal) and consume the whole recording. Captures from macOS replay on Linux and the other way round: the recorded platform facts travel with them, and on replay nothing calls the system. A recorded failure keeps its errno as the recording system numbered it, and `file::recorded` makes it the same error on the other system (its text keeps the recording system's words and number): code compares a replayed error's number through `system::errno`, not `raw_os_error`, and copies an error with `system::copy`.
- **App replay** (slower, XCTest): the test runs against its app journal. Requests the app makes must match the recording; inputs (helper replies, terminal output, process exits) come back in recorded order; observations answer what the recording saw at the app's own progress, not a later or earlier state. A test's waits (`TestSupport.eventually`) continue where the recording's did: the recorded step says where the test checked its condition, replay holds back what came after that check until the test steps, and a check that keeps failing on the settled state frees the held input in rounds. What a terminal's renderer hands back (the bytes typed into its pty) comes once the app typed them, so replay never types ahead of the test, and focus reports are ignored on both sides. The exact hold-and-release rules (which inputs a running check may see, how typed bytes are matched, when a pty size gates input) are documented beside the code in `Dispatch/Helper/AppReplay.swift`. Recordings made before steps carried `end` keep the older, looser rules until recorded again.
- **App <-> helper check**: both sides of every connection carried the same bytes.

  ```sh
  "$HELPER" capture check build/captures/<TestFile>/<testName>
  ```

  It pairs app lifetimes with helper stdio, spawned children with their helpers, socket connects with accepts, and hook senders with the hook server's messages (by pid, or by the datagram's bytes); prints each pair (`equal`, `stopped reading`, or `DIFFERENT from byte N`) and `linked to the app journal: X of Y captures`; and exits non-zero on a difference or an unlinked capture. `question 1 answered without a record by the hook server` is a known gap: the hook server answers "does this helper own the asking process" without recording it.

## Migrations

The corpus is test data generated by the code, so a change to what recordings hold ships with a migration, as a schema change ships with a database migration. `test/replay-migrations/` holds them in order (`NNNN-name.json`), with the wire dictionary of every schema the corpus was recorded with (`wire/<schema>.json`, written by `dispatch-helper capture dictionary`). The corpus lists the ones it has had in `replays/MIGRATIONS`; a corpus without that ledger has had the baseline only. `dispatch-helper capture migrate replays test/replay-migrations` applies the pending ones in order (`--check` lists them, `--dry-run` reports what each would change); the Debug build and `test/xcode.py` run it before they replay, so the corpus's own `git status` shows what a migration did, to commit with it.

Every migration says `why`, and is one of:

- **`wire`**: a new wire generation (a breaking change; additions need none). Every capture of an older generation is written in the current one from its dictionary (`capture convert`), with reviewed `edits` for what a token rewrite cannot express (`write-parent`).
- **`rewrite`**: what the app sends changed in text only (a setup script's wording, an argument's spelling). In the inputs the app recorded (`open.*` records: commands, helper launches) each `old` template becomes its `new` one, as written and as shell-quoted inside `'…'`; `{{name}}` slots carry a digest, a session, a staging folder or a size across. Recorded results are never rewritten. A rewrite is right only where the new code would get the answers the old one got, which replay then checks: an input no template matched still differs, and its test fails until it is recorded again.
- **`rerecord`**: the answers changed (a new or reordered request, a failure that now says why, a default that lists other files). The listed tests' recordings move out of the corpus (to `build/retired-replays/<migration>/`), so they run live until `test/run.sh --capture` records them again; nothing is deleted.
- **`encode`**: how the corpus is stored changed (zstd `rsyncable`, written by the macOS capture tool, so a later change to a file is a small git delta). Every capture is written again with the same records.
- **`baseline`**: the corpus as migrations found it.

A migration's `fingerprints` name what the code generates for recorded inputs once it applies. Two tests hold the code to them: `ReplayMigrationTests` fingerprints the SSH setup scripts, every git request the files data layer makes, and the defaults that decide what files mode lists; `the_current_schema_has_its_dictionary_and_migration` (capture tool) checks that the code's wire schema has its dictionary and the last migration naming `wire` names it. Changing any of them without a migration fails there, with the fingerprint the new migration should name, instead of failing case by case at replay.

Writing one: decide which kind the change is by what the recordings held (a rewrite when every recorded answer still holds; otherwise the tests whose answers changed are rerecorded), add the file with the next number, apply it to the corpus, replay the affected classes (`test/vm.py test <classes>` replays them from the corpus) and add what still fails to a `rerecord`. Commit the migration with the change, and the corpus with its ledger.

## The capture tool

`dispatch-helper capture <command>` exists only in a helper built with the `capture` feature (Debug builds: `build/helper-rust/bin/<platform>` and the app's bundled `dispatch-helper`). Its replays run the same executable, one process per capture, so the tool and the helper it checks are always one build. A helper built without the feature has no `capture` command and refuses to start with `DISPATCH_REPLAY`. Options (`--limit N`, `--output DIR`, `--dry-run`, ...) go anywhere after the command.

```sh
cd helper
cargo build --offline --package dispatch-helper --features dispatch-helper/capture
HELPER="$PWD/target/debug/dispatch-helper"
```

- **Read a capture.** `inspect` prints one line per record: its number (app replay messages name the same `record N`), milliseconds since the capture started, section, operation, what was asked, then `->` and what came back. Our own frames print decoded, one line per frame (`request 45 terminals.attach {size: ...}`, `notify 45 terminal.output {...}`, `cancel 45`), so `grep` finds a method together with its record; a frame split over several reads prints whole on the record where it completes, and a streamed reply prints its chunks and then the whole message. Other bytes print as text when UTF-8, as the value when they are one of our plain values, else hex. A capture without its footer is cut (its process ended mid-write or is still running). `value` prints a mismatch file, `key` a directory's keys, and `diff` compares two captures (or two directories, paired by their records whatever their names) on what `inspect` decodes, text and bytes word by word, grouping the same change wherever it occurs; both sides must be of this helper's wire version.

  ```sh
  "$HELPER" capture inspect replays/ChatTests/testX/<key>.rpl.zst --from 280 --limit 20   # around a replay message's record 290
  "$HELPER" capture value results/000003.mismatch/mismatch.value
  "$HELPER" capture key replays/ChatTests
  "$HELPER" capture diff old/<key>.rpl.zst new/helper-<pid>-<start>.rpl.zst   # or two directories of captures
  ```

- **Search** every text and bytes value, keys included, for a literal, case-sensitive substring: `"$HELPER" capture grep '/Users/' replays`, `"$HELPER" capture grep 'Authorization' --limit 50 build/captures`.
- **Replay helper captures**: `"$HELPER" capture replay replays --completion required --output results/replay-01`. `report.jsonl` has one row per capture: `status` (pass, fail, timeout, or skip: nothing to replay), the replay's exit, its completion receipt, a diagnostic and, on a mismatch, the expected and actual operation as a value.
- **Migrate**: `migrate REPLAYS MIGRATIONS [--check] [--dry-run]` ([Migrations](#migrations)); `dictionary DIR` writes this helper's wire dictionary.
- **Store, prune, check, scrub**: `store STAGE REPLAYS --tests DispatchTests`, `prune REPLAYS [--dry-run]`, `check PATH...` (above), `grep PATH... --needles FILE [--jobs N]` and `replace DIR OUT [--needles FILE] [--ips] [--uuids] [--jobs N]` ([scrubbing](#scrub-captures-before-sharing-them)).

## Reading a failed app replay

- **Stall** ("no recorded event was reached for X while the app was idle (capture reached it after Y)"): the app was idle (every queue the journal feeds answered, no live work running) for 4x the time capture took to reach the next record, at least 3 seconds, and nothing came. The message prints:
  - `frontier`: the first record replay is waiting for. An `open.*` or `out.*` there is something the app never did; an `in.*` an input nobody listened for; an `in.slave.read` typing the app never did (its lifetime line shows what it typed instead); an `open.step` the test's wait, with its source line.
  - `recent`: the last records replay consumed, and `stale observation`: an observation answered with an older recorded value than the newest one.
  - One line per lifetime with its next record, what the app `typed` into a renderer that no hand-back took yet, and why its next input is `held`: usually a pty size the app's layout never gave that view (`the app's pty is 31x42; recorded 32x42, later 30x42`). A size capture's layout passed through for a moment that replay's never produces is a flash on screen: find and fix it in the app. A view in no window holds without holding the other lifetimes (`in no window: the others go on`).
- **Mismatch** ("expected X, received Y"): the app did something else than the recording at that point. Both events are written to `build/replay-diagnostics/<test>-<journal>.mismatch-<id>.rpl.zst` (`capture inspect` reads it); the message names the file.
- **"made ids differently"**: a site made another number of ids than in the recording, so later ids from that site shift. Usually the symptom of an earlier divergence, not its cause.
- **"relaxed"**: requests replay answered or dropped because UI timing differed from the recording (listed, not a failure by itself). "after its end X": the app sent X after replay delivered the connection's recorded end; nothing answers it. "size not reached on lifetime N": replay was about to stall on a pty size the app's layout never gave that view, so its held input came at the app's size (a passing replay never gets there). "answered X" / "unrecorded X": the app sent X and the recording lacks it; replay gave the recording's answer when unambiguous, else "unavailable". "unanswered X": an equal X the app sent earlier is still open in the recording, so the new one gets no answer, as in capture. "unsent X": the recording has X and the app never sent it; X changed nothing on the helper (cancelled before anything came back, or refused at once), and an equal request sent much later counts as a later one.
- A replay that passes prints "App replay verified: <test> (longest wait <idle>, capture <gap>)": of the idle times that ended with a record reached, the one furthest beyond 4x what capture took for that record. The stall bound is measured against these.

**Finding the cause.** Start at the first difference the failure names (for a helper capture, `mismatch` in `report.jsonl`) and read the recording around it (`inspect --from 280 --limit 40` for record 300). Then compare the old recording with a new one of the same test (`--capture` it live and find its file in `build/captures/<TestFile>/<testName>/`): `capture diff` groups the ids, pids and uuids that differ in every run. When the two were recorded with different wire versions (a merge changed the protocol), each side needs its own helper's `inspect`, and the numbers that differ in every run (record numbers, times, lifetimes, request ids, pids, uuids) are masked so only real differences remain:

```sh
norm() { "$1" capture inspect "$2" --limit 100000000 | sed -E 's/^[0-9]+ [0-9.]+ //; s#app/[0-9]+#app/L#g;
  s/(request|response|notify|cancel) [0-9]+/\1 N/g; s/[0-9A-Fa-f]{8}(-[0-9A-Fa-f]{4}){3}-[0-9A-Fa-f]{12}/UUID/g; s/[0-9]{4,}/N/g'; }
diff <(norm "$OLD_HELPER" old/<key>.rpl.zst) <(norm "$HELPER" new/<file>.rpl.zst) | head -100
```

- The first block that differs is usually the cause; the rest follows from it. Terminal bytes are split differently in every run: compare what a stream carried, not where reads split it. Compare the app's own log lines of both runs (the XCTest output of that test) too: they show which code path it took.
- Recordings of another wire version decode only with their own helper's tool: before a protocol change or a merge, copy `replays/` and the helper built from the old checkout (with `capture`) outside the checkout.
- **Intended change**: delete the test's old recording and keep the new one (`--capture`, then `--replay` it once). **Not intended**: fix the code and replay the old recording again until it passes; no live run needed. **Many tests changed the same way** (one shared request, a renamed field): fix or accept that one cause first, then replay all again; most of the other failures go with it.

### A test that fails live sometimes

A test that fails only now and then is a race in the app or the test, often one users can hit too. A recording turns it into a repeatable failure: run with `--capture` (`build/captures/` keeps every test's journal and helper captures, failed ones included), then `python3 test/xcode.py --replay DispatchTests/Class/testName` replays the failed test from its own journal: the same inputs in the same order, so the same path and the same failure, every time. Find the difference against a passing recording of the same test as above. Then ask the app why: add log lines around the suspected decision, rebuild and replay the failed recording again. Log lines change nothing the app sends or asks, so the recording still applies, and the replay prints the reason in seconds instead of waiting for the race to happen again live. A fix that makes the app ask the outside world something new (another process query, another file read) gets "unknown" from an old recording: confirm it with live runs and record anew. Example: ssh typed in a terminal sometimes hung; replaying the failing recording showed the launch request was refused because the process probe took ssh's own forked ControlPersist master (same process group) for the user's ssh.

## Writing tests that replay

- **I/O goes through `System`** (`observe`, `act`, `run`, `sleep`, `pty`): whatever bypasses it is invisible to the journal and makes replay diverge.
- **Facts about the machine come from `System` too**: `home`, `temporary`, `checkout`, `bundle`, `executable`, `resources`, `environment(name)`, `inherited`, `path`, `machine` (the account's name, home, shell and quiet login, the machine's name and memory; `machine.launch` is what the terminal engine reads of the machine), `pid`, `uid` and `resolve(url)` (a link resolved is a disk read). While testing they name paths in the run's private root (`/tmp/dt-journal`: the test home, `tmp/`, and `checkout`, the runner's link to the checkout), the same on every Mac, so recordings replay from any checkout and account. `test/xcode.py` refuses to run when app, test or terminal engine sources read them directly (`ProcessInfo...environment`, `NSHomeDirectory()`, `temporaryDirectory`, `Bundle.main` paths, `NSUserName()`, `resolvingSymlinksInPath`, `#filePath` as a path, `gethostname`, `physicalMemory`, `processInfo.hostName`, `getpwuid`, `Machine.current`) outside `System.swift`, `AppReplay.swift` and the engine's standalone parts, and lists the lines. A fact read live where a recorded one meets it breaks replay on any other Mac, and after scrubbing on this one (the engine once compared the recorded OSC 7 host with the live `gethostname()`).
  - Configuration that exists only on the recording machine (the Linux host profile, the account name) is read through `System` (`read`, `exists`, `machine`). So is a bundled file whose content reaches what the app sends: the SSH helper's digest and size name its remote cache path in every bootstrap command, so they are observed (`payload`) and a rebuilt helper changes no recording. A test that names that cache path or compares its bytes asks the same observation (`BootstrapFixture.payload`), never the bundled file itself.
- **Wait with `TestSupport.eventually`** (or helpers built on it), never a bare sleep for I/O: its step is where replay continues the test.
  - Wait for everything the next action depends on, not only what the screen shows: a prompt sent before its chat's history arrived names no conversation, by timing.
  - A test's own I/O that is not recorded (an in-process pipe) has no order against recorded events (a replayed timer ends at once): wait for it with a step before what it races.
  - A wait does not end while the sidebar slides (`TestSupport.eventually` also checks no split's `sidebarAnimating`): the slide runs on wall time, so layout read or changed during it differs between runs.
  - What a wait's condition asks the outside world (a fixture's `tmux list-panes`, any query made while `System.polling`) is a read, answered with what capture saw as far as the app got, never by count: how often a test checks is wall time.
- **Work a test does live on purpose**, in replay too (real shells running the app's wrappers), runs inside `AppReplay.live`: the journal does not see it, and without it the watchdog calls the app idle while it runs. A test runs a process to its end with `TestSupport.live` (inside `AppReplay.live`) and starts one beside it with `TestSupport.start`; one whose result the recording depends on is recorded instead (`System.run`, `System.Child`, `TestSupport.fixture`, so replay starts nothing). `test/xcode.py` refuses `.run()` or `.waitUntilExit()` in test sources outside TestSupport and lists the lines.
- **A fake standing in for recorded work** (`SSHStatisticsStoreTests.Provider`'s `sample`) takes its time through `System.sleep`, never `Task.sleep`: on wall time, identical timers take each other's recorded wakes.
- **Every `System.sleep` (and `SSHTimeout.run`) names its timer** (`System.sleep(for: interval, "poll")`): a recording knows it by file and name, so editing other lines of the file keeps the recordings that use it. In the app, a timer that bounds I/O (`SSHTimeout`) sleeps through `System.sleep`, so a replay times out exactly where its capture did, never on its own clock; a sleep the capture's caller cancelled ends in replay only when its caller cancels it.
- **A race the app decides** between its own work and what a helper reports (a queued attach whose tab may have moved on) is recorded where it is decided (`System.observe("bound", terminal)`): the app then sends what its capture sent. Values the app reads from its layout into a request are not decisions to record: a request's `size` is never compared (geometry follows drawing), and screen publications and resizes are acknowledged by replay itself. A request the recording lacks points at such an unrecorded decision.
- **An order the app waits for** so that identical requests go out alike (a chat setup's launches.list after its helper's discovery) must not wait for anything a stop waits for: a test's next case can start while the previous one still stops, and a helper made then discovers only after that stop (a deadlock, live too). Check such a change with a full run: a test run alone never starts during a stop.
- **Work must not depend on when SwiftUI renders**: a shown tab's terminal is created at the layout commit (`HelperWorkspace.present`), a terminal view attaches only to a host whose container is in a window, and a split keeps its divider share (resizes never re-derive it from rounded frames).
- **Ids come from `System.uuid()`**: replay makes the same ones per site.
- **End helpers by closing their stdin** (EOF). A stdio helper still running when the app's grace ends gets SIGTERM and finishes its capture before it exits; SIGKILL loses the rows it had not written yet. At EOF a stdio helper also ends the control streams its client fed, so a tmux command waiting on one fails instead of keeping the helper alive.
- **No state crosses cases**: each journal replays alone. Every case starts from the same app state: `TestSupport.isolate` empties the process-wide caches that decide what the app asks its helpers (the host backend cache, the chat's launches and integration facts), and `TestSupport.launches` turns every integration off (off, not "nothing turned off": installed hooks stay in the test account between cases). A case that tests an integration turns it on itself (`TestSupport.integrations`); what it leaves on is turned off at its end, after any runtime stop the case began has ended. The app is active in every case. Every case ends with the same teardown whether it replays, records or runs live: the app runtime stops and its shutdown work (launch mailboxes, SSH masters, helpers) finishes inside the case, never in the next one's journal. Fixture code that does real file work in replay (copying helper resources into a test server's root) must not rely on its recorded cleanup: the next replay of the same recording finds the leftovers. TestState reports any other change a case leaves behind.

## Scrub captures before sharing them

### Automatic scrub

Every recording reaches the corpus through `test/xcode.py --capture`, and that stores it through `test/scrub.py`: nothing recorded on this Mac goes into `replays/` unscrubbed.

- **Needles.** `test/leak.py` lists what a run may record about this Mac and its SSH test hosts (below). Values that change by themselves are needles with no decision: machine, boot and kernel ids, network addresses, time zones, key fingerprints, the SSH agent socket, login banner times. Every other value (accounts, host names, names, paths, git identity) takes one decision, kept in this Mac's private policy file `~/.config/dispatch/replay-scrub.txt` (or `DISPATCH_SCRUB_POLICY`), never in a checkout: `needle<TAB>stand-in` of the same byte length or a bare `needle` (masked) for a private value, `#public<TAB>value` for a public one. Choose stand-ins as below (step 3); the corpus uses `test.local` for this Mac.
- **Fail closed.** A value with no decision, an SSH test host `leak.py` could not reach, or a credential-like variable (`TOKEN`, `SECRET`, `PASSWORD`, `API_KEY`, ...) in a recorded environment stops the store; the run's tests stay in `build/captures/`. Decide in the policy, then `python3 test/scrub.py store build/captures replays`.
- **Then** `capture replace` with those needles (it replays every helper capture before and after), a plain search of the output for every needle, and `capture store`. App journals get the same substitutions: replay their tests before pushing.
- **Before a push.** `python3 test/scrub.py hook` installs a pre-push hook in `replays/` (and this checkout) that searches every capture a push adds for this Mac's needles, and refuses the push if one holds any. `python3 test/scrub.py check [PATH...]` searches the whole corpus (about a minute); `python3 test/scrub.py tests replays Class/test...` scrubs tests already in the corpus, in place.

### By hand

Keep the original captures private. Find the private values yourself and name them as needles; `capture replace` rewrites exactly those, then checks that the helper still replays. There is no allowlist or denylist: agent output is arbitrary user and model text, a list of public words never ends and goes stale, a list of private words misses the next account, host or path, and masking blindly changes what parsers see. Only UUIDs and IPv4 addresses are found by their shape (`--uuids`, `--ips`). Process lists are the exception: a needle hides only the token it names, so `replace` removes every row of a statistics process list but the processes the tests need (`ALLOWED` in `helper/bin/src/capture.rs`). Captures come from real runs: never edit recorded I/O to make a check pass. A passing replay proves behavior for this helper and these captures, not that every private value was found.

1. **Build the helper with the `capture` feature** ([the capture tool](#the-capture-tool)) and work in git-ignored `tmp/review/` (`umask 077; mkdir -p tmp/review`). Replay with the current helper first: a capture replays on the latest helper or is dropped (`capture prune`). Put every related capture (local and SSH helpers, app journals of the same case) in one input directory, copied, not linked (the tool does not follow symbolic links and lists them on stderr): one invocation gives every file the same substitutions. `grep` and `replace` read the captures `--jobs N` at a time (default: every core).

2. **List what a run may record**: `test/leak.py --suite full > tmp/review/needles.txt` (the same arguments as `test/run.sh`; the tests read their hosts from the checkout's profiles, so every profile is included whatever the selection). For this Mac and every SSH test host it prints account and full name, home and temporary directories, host names, machine/boot/hardware ids, network addresses, SSH host key fingerprints, git identity, the time zone (with a random real zone of the same byte length as its value, and a warning below 10 zones of that length; a zone no other shares its length with is handled by hand; UTC gives none), their parts (path components, host name labels), each machine's prompts (`account@host`), its shell startup files linked elsewhere, what `ssh -G` resolves per profile, and this Mac's login session's launchd agent socket folder. After the recording, `test/leak.py … --captures build/captures` adds each login time the banners show ("Last login: Fri Oct 16 14:44:47 on ttys007"), with a distinct same-shape time on 1 January 1970 as its value. A host it cannot reach is printed as `NOT REACHED`: its values are missing, not absent. Process lists are printed as `#` comments: copy their private parts as needles. Environments are not printed (they can hold credentials): `capture grep` lists the helper's. Recordings made before the runner handed tests UTC and `en_US.UTF-8` hold the account's own locale (its languages, its region, its terminal's `LC_TERMINAL`): name those values, with same-length values. Delete the public values the draft holds (`Users`, `home`, `tmp`, `com`): a short or common needle changes public syntax and fails the replay check.

3. **The needles file**: one needle per line, a literal (no patterns), searched everywhere, inside larger names and paths too; at one position the longest needle wins. Lines starting with `#` are comments. `needle<TAB>value` replaces the needle by that value, which must have the needle's **byte length**: lengths around a value are recorded too (wire frame and value lengths, sizes, terminal columns), so another length breaks every frame it is in. `needle<TAB>needle` keeps a value `--ips` or `--uuids` would replace. Without a value the needle gets a mask of the same length and shape: each letter and digit is replaced by another of its kind (case kept), other characters stay, a UUID or IPv4 address gets a random one of its kind, from a fixed pseudo-random stream per needle position, so the same file always gives the same output and a replacement never equals a needle or another replacement. A mask keeps the needle's shape (`robin07` gives five letters and two digits; a host name keeps the lengths of its labels), and a guessed value can be checked against that shape: choose the replacement yourself (`needle<TAB>value`) wherever the shape says something (names, host names, accounts), and take the mask only where it says nothing.

4. **Search**: `"$HELPER" capture grep replays --needles tmp/review/needles.txt > tmp/review/found.txt` (or one needle before the paths; literal, case sensitive). Every text and bytes value of every record is searched, map keys included, the way a reader of it sees it, on views: a stream is one view across its records (one side of a connection, and inside our frames each text or bytes per method, path and terminal), so a needle a record or frame boundary cuts in two is found whole and listed as `(cut)`; line breaks and CSI sequences are not part of a view, so a needle a terminal wrapped is found and listed as `(wrapped)`; and every terminal stream is drawn on a screen of its recorded size (as Ghostty draws it: autowrap, scroll regions, the alternate screen, wide characters, rewrap on resize), so a needle a program drew cell by cell over text already showing is found there and listed as `(screen)`. `(screen, shared)` means a cell is tied to other text whatever value replaces the needle: record the test again until `grep` shows no shared cell. Herdr's base64 `terminal.frame` and `terminal.input` fields, tmux `send-keys -H` hex pairs and masked websocket client frames (the helper's requests to Codex's app-server) are decoded and searched; a needle cut across two of their lines or frames is not found, and base64 or hex other programs wrote (ids, keys) is not decoded. Streams that name no size (protocols, text of ours) are drawn on a screen of no size and listed under `screens of no size`. The output, in order:
   - **The helper's environment**: every variable each helper recorded at startup and its distinct values, with file counts and the first `file:record`. Recorded whole, before any scrub; no needle or shape finds a credential nobody listed. Read every value: private ones are needles.
   - **Encoded text**: every text shaped like hex, hex pairs or base64 (16 bytes and longer) outside the fields above, per place, most frequent first. Needles are not searched inside them and `replace` does not change them. Judge each: another program's encoding holding no private data is fine; private data inside an encoding, or an encoding our own helper or app made, is a finding to fix at its source, never worked around in `replace`.
   - **`--values SHAPE`** (any number of times): every distinct line at places holding SHAPE, digit runs as `#`, for values nobody listed yet (network interfaces: `--values 'network[].name'`). Process lists need no review.
   - **Per needle**, its matches with per place (section, op, field, and inside our frames the method and field) how many, in how many files, and the first with up to 80 bytes either side; then the whole tokens holding it or its replacement (a path component, a name, a host), which is what a mask leaves standing (`<mask>-collector`): name the rest too, or the whole name.
   - The needles' counts come last: what a scrub must bring to zero. Lists stop at `--limit` (default 200). The output contains the private values: never attach it.

5. **Replace and verify in one command.** The output must be a new directory:

   ```sh
   "$HELPER" capture replace replays tmp/review/attempt-1 --needles tmp/review/needles.txt --ips
   ```

   - `--ips` replaces every IPv4 address of a machine (not `0.x`, loopback `127.x` or `224` and up) by a random valid one with the same digit counts; `--uuids` every UUID by random hex digits (version and variant kept). Needles win over both. It prints every value they found with its replacement: review the list (a 4-part version looks like an address, and so does `27.0.0.1`, the rest of a `127.0.0.1` a read cut in two) and keep such values with `value<TAB>value` lines. **`--uuids` breaks replays wherever an id is made rather than read**: the app makes most of its ids from the seed its journal records and the helper formats some from recorded random bytes, and those no longer match their replaced copies. Use it only for captures nothing makes ids in; otherwise list the private UUIDs as needles (machine and boot ids come from `leak.py`).
   - Replacements depend on the order values are met (files sorted by path, records in order), never on the value: the same input gives the same output, the same value gets the same replacement in every file, and a case's app journals and helper captures scrubbed in one run stay linked.
   - It first masks process names: in every statistics process list (an array of objects with `pid`, `name` and `rss`: the stats job's result, the reply frame, a reply in chunks, a remote host's bridge passing it on, the app's reads of it) each name but `ALLOWED`'s becomes as many `x`, in place. Every row and every frame keeps its length (a shorter reply would make a helper write a large one in fewer rounds than it recorded), and nothing is encoded again (an older recording need not encode as this helper would). A name that is one of our schema's words (`route`) stays: the helper sends it as its number. Rows carry a name, never a path. A name the app or a test needs (a test reads `yes` from the list) goes in `ALLOWED`. Then literal bytes change on the same views as `grep` reads (a cut or wrapped needle has each byte replaced where it was recorded; the herdr, tmux and websocket fields are decoded and encoded again in the same length and case; a field that cannot be decoded is listed as `NOT DECODED`, never skipped silently). Then hashes follow: for every value of its own `replace` changed (a command's output, a file), its SHA-256 before is replaced everywhere by the SHA-256 of what it became (an SSH configuration's fingerprint is the SHA-256 of `ssh -G` output), and it prints how many it followed. A hash of built-up text (parts joined, lines filtered) is not followed, and neither is an id hashed from part of a value (the helper ids Codex records by the SHA-256 of a transcript line, and keys Pi's history by its session header): keep such values out of the capture (tests run with `TZ=UTC`, since Codex writes the time zone into its lines) or leave them as recorded (dates in Codex transcripts), else the app replay fails and the recorded hash confirms a guess.
   - Then every helper capture replays as recorded (`tmp/review/attempt-1.replay-original/`) and as rewritten (`.replay-candidate/`). A capture the scrub broke is `BROKEN BY THE SCRUB` with the record and op it stopped at and its mismatch file (`capture value FILE`); one that does not replay before the scrub either is `NOT CHECKED`. Either exits non-zero.
   - Last, every output file gets a random name (`.rpl.zst`, zstd level 9 with the long window, as the corpus keeps it): a content key kept on a changed capture would confirm any guess at what the scrub replaced. Until that step (and on any failure) the output files keep their input names, so the reports name the same files as the input. A needle in a record's section or op is refused: those are names the helper itself chose.
   - App journals get the same substitutions, but only their app tests can replay them: run those tests (on the Mac) before relying on them.

6. **Check with plain tools too.** Captures are zstd around our binary records, with no hex or base64 layer of ours, so `zstd` and `grep` see every literal needle but those cut, wrapped or inside the encodings above (which `capture grep` sees):

   ```sh
   grep -v -e '^#' -e '^$' tmp/review/needles.txt | cut -f1 > tmp/review/plain.txt
   find replays -name '*.rpl.zst' -exec zstd -dcq --long=27 {} + | LC_ALL=C grep -aoFf tmp/review/plain.txt | sort | uniq -c
   ```

   Before the scrub it counts each needle; after it, it must print nothing (but the values kept with `value<TAB>value`).

7. **Review the candidate again before publishing.** A zero exit means replay succeeded, not that the files are private. `grep` the candidate for the needles, the broader shapes (`/Users/`, `/home/`, `@`) and its encoded texts again, and read terminal output and user/model text. Replay reports and logs beside the output name original paths: keep them private, and attach only the reviewed candidate captures.

**If verification fails, keep the evidence and find out why.** Never skip the check or drop a capture. If an original fails, the helper or the capture does not match: replay with the run's own helper first. If only the candidate fails, the needle changed syntax, a relation the helper or app derives (lengths, a hash of built-up text, parsed numbers, case changes, sorting), or a value that also sits in another program's encoding the helper decodes (`grep` warns of it): inspect the original at the record the replay names, pick a narrower private component and start again from the original. If a value cannot be replaced without changing behavior, capture the scenario again with a non-private account or path.
