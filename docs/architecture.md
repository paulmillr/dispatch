# Architecture

Each rule here guards against lost sessions, misdelivered input, or leaked data. Build and test mechanics are in the [README](../README.md#quick-start) and [test/README.md](../test/README.md); tmux, herdr, SSH, and agent lifecycles are in [integrations](integrations.md).

| Owner | Owns |
| --- | --- |
| [AppDelegate](../Dispatch/AppDelegate.swift) | Wiring, restoration, shutdown order. |
| [Workspace](../Dispatch/Workspace.swift) | Spaces, panes, tabs, selection, host placement. Related mutations publish together through `updateLayout`. |
| [TerminalRuntime](../Dispatch/Terminal/TerminalRuntime.swift) | The terminal engine and its surfaces, keyed by stable UUID. |
| [Hosts](../Dispatch/Hosts/) | Presentation identity, kept separate from live process ownership and connection recipes. |
| [SSH](../Dispatch/SSH/) | Enhanced-connection authentication and per-connection feature grants. |
| [Helper](../Dispatch/Helper/) / [Herdr](../Dispatch/Herdr/), over the helper's [tmux](../helper/multiplexers/tmux/) and [herdr](../helper/multiplexers/herdr/) crates | Mapping server-owned sessions into native spaces and tabs. |
| [Chat](../Dispatch/Chat/) | Agent discovery, per-surface sessions, drafts, submissions, approvals. |
| [Views](../Dispatch/Views/) | Presentation only. Views never own shell lifetime. |

The Mac and iOS apps compile common model, parsing and protocol cores from `Dispatch/`; `project.yml` lists the
phone's shared files explicitly. Native presentation, connection generations and process ownership remain with each
app. [Shared sources](ios.md#shared-sources) describes the boundaries; portable regression cases compile in both test
targets. Terminal rendering/configuration work shared by the native adapters lives in `TermApple`.

## Invariants

- **Threading.** Workspace and UI coordinators are `@MainActor`. Blocking I/O, process inspection, and heavy parsing run on transport actors or background workers that report back to the owning coordinator.
- **Identity.** Host changes, reorders, splits, and Terminal↔Chat switches preserve surface and conversation identity. Presentation changes never relaunch a shell or acquire input authority.
- **Tabs only.** With Settings' "Vertical tabs, no spaces" (`Preferences.tabsOnly`) the sidebar lists rows (`Workspace.sidebarTabs`), and a row is what the window shows when it is chosen: a native tab, a tmux or herdr window (its panes a line each), or a split, a native space whose two to four panes hold one tab each, listed as one row (the space's id) with a line per tab in reading order, each led by a glyph of the layout with its pane filled. A line's click focuses its pane. Splits are made in the sidebar: ⌘- and ⇧-clicks mark rows (`sidebarMarks`, view state, never saved; the first ⌘-click marks the active row too), and the context menu's Split N Tabs or ⌘D splits them, at most four, the menu naming the reason otherwise. Native tabs on one host move into a new space where the first stood. tmux or herdr windows of one session move into a space of their own (the first window's when it is alone there), which only retags them on the server (a tmux-backed space is a group of the session's windows, `@dispatch-window`), and once they are all there (`pendingWindowSplits`) Dispatch shows them side by side, one window group each (`TabPresentation`): such a space is a split row with a line per window (`Workspace.windowSplit`). No pane, window or session is created or merged; native tabs and windows never split together. No pane of a split holds a hidden tab: ⌘T while a split shows makes a row in the nearest space of plain tabs on its host (`homePane`, else a new space after the split); ⌘D on a tab among others moves it to a space of its own before the new tab splits beside it; ⌘D in a split pops out the panes it would merge. A tab dropped on a split's line joins it (Two Above One, then Grid) or, already in it, trades places; Pop Out, Separate All and dragging a line out make tabs rows again, and a split down to one tab is a plain row. A split of windows takes no new window (⌘T makes it in the session's nearest other space, `windowHome`), Pop Out moves a window there, ⌘D in it adds a window beside, and ⌘D on a window among others moves it to a space of its own first. Window groups side by side that are no such split (made while spaces showed) fold into one strip while tabs only is on, Dispatch's state alone. Spaces still own layouts and backends. While tabs only is on, every layout commit lifts a tab left behind a split's pane (a split made while spaces showed, a restored one, a tab a command moved into a pane) to a row of its own, where Pop Out would put it (`liftHiddenTabs`): a row a pane hid could only show by swapping another out of the list, so ⌘] would land on the split again and again. The rows are listed in the order the sidebar draws them, under each row's own host when grouped by host, and ⌘1…9 and ⌘[ / ⌘] walk that order, wrapping. A window row dragged before or after another moves there on the server, within its space or into another; a window arriving in a space's strip takes its server place (`TabPresentation.reconcile`), so one dropped before a space's first window is first. Listing spaces, `sidebarTabs` stays one row per tab (the Nautical radar). With no strip to tint, a remote tab's host edge crosses the content's top only while the sidebar is hidden: its row marks the host otherwise.
- **Automatic tab names** (`TerminalTab.displayLabel`, `ContainerTab.displayLabel`; the phone's `MobileTab.label` uses the same `TerminalTab` rules) follow what Files shows while the tab shows it (`FilesTab.tabName`, both apps: Files the open file with its folder, `auth/token.ts` or `~/notes.md`, else the folder browsed; Review "Review" and the branch; Commits the open commit's subject, shortened to 48 characters, else "Commits" and the branch), else the agent's conversation title, then the program's own title or the multiplexer's name, then the folder at a prompt. A numbered tab takes its focused pane's title unless it names the folder or repeats the tab's name, else the folder, else the tab's name (`paneLabel`). The typed launcher's name (`dispatch-helper launch claude` on an SSH host: tmux names the window after it, the helper's own terminals after its path) shows as the tab's agent (`shown`): the key Chat bound, else the one the topology's binding names (`agent(named:)`, from the executable, the pane's and the window's names), so it shows before Chat binds and with Chat off.
- **Server-owned sessions.** Detaching a native view from tmux/herdr is not terminating server work. Backend snapshots reconcile existing presentation identities in place.
- **Remote trust.** Host grouping is presentation, not a permission boundary: grouped aliases can have different grants. Remote operations carry authenticated connection/process identities and generations, and a remote PID is never a local PID. Agent hooks on a remote connection need that connection's grant. Ordinary SSH works without the helper.
- **Screens.** The Mac never publishes screens (`terminals.publish`) for the tmux and herdr terminals of a helper whose hello accepted `screens.host`: that helper reads them from the multiplexer, and one publication would turn its host reads off for that terminal. It publishes native terminals and SSH logins a helper observes in a tab, and everything to a helper without the feature (`HelperWorkspace.publishes`); a terminal that publishes to nobody reads no screen until that changes (`TerminalView.wakeScreens`).
- **Hidden terminals.** A hidden terminal's output is held on the host, never dropped silently: showing it again restores the screen. A chat tab whose terminal is not on screen may stop its subscription's output (`terminals.follow` false, helpers that accepted the feature, tmux and herdr only); following again gets that subscription alone a whole repaint before any later output, and input, exits, chat records and the host's screen reads go on meanwhile. Plain terminal tabs always follow. While output to the app is backed up the helper still reads and runs its requests (`requests.backlog`: keystrokes, cancels, `terminals.follow false`, pings; up to 256 waiting replies or 1 MiB), so a flood in a visible pane delays only the replies, not what the requests do. An output window (`terminals.window`: at most 256 KiB of unacknowledged terminal output per client, acknowledged per attach subscription by `HelperOutputWindow` once handed to the terminal (batched while streaming, flushed when quiet), the multiplexers paused past it) exists but is off by default (`HelperSession.outputWindow`; the "Slow connection mode" setting turns it on for new connections). Before turning it on by default, move the acker's flush timer (a `DispatchQueue` delay today) onto `System` timing so recorded tests can enable it, and measure again over a shaped link ([benchmarks](benchmarks.md#ssh-over-a-slow-or-lossy-link)).
- **Hidden terminals' GPU memory.** A terminal whose tab is not shown (another tab or space, whose view leaves the window, or Chat/Files covering it) keeps its process, screen and history but gives back its drawing memory 5 s after it was first reported hidden (`HiddenResources.retention`; repeated reports do not restart it): the swap chain's IOSurfaces and the layer's frame, the renderer's buffers, atlas and image textures; quicker switches keep them. Showing it again draws a frame synchronously before the view appears (one the GPU finishes late is shown when it does), so no empty frame shows. A terminal that is shown in its tab but whose window is covered or minimized releases only on memory pressure, and then keeps its last frame as the layer's contents, since the window server can show it again before the app hears it is visible. Every hidden terminal releases at once on a memory pressure warning. The phone releases its renderer's buffers and textures the same way (its layer keeps the last frame). Terminals on one GPU share the shader library and pipelines (`MetalRenderer.pipelines`).
- **History memory.** Page blocks no page uses (cleared or reflowed history in a page list's pool, a closed terminal's in `SharedPageBlocks`) are marked `MADV_FREE_REUSABLE` (`PageBlockMemory`) until a page takes one again, which zeroes what it uses: the system may reclaim them and the footprint does not count them. Scrollback in use is not compressed (Ghostty 1.4 compresses idle pages; measured, history pages compress to 2–4% with LZ4, a candidate once the page store's access paths are settled).
- **Off-screen chats.** While a chat's main window is off screen (ordered out, or the app hidden; not minimized), its transcript keeps the rows it showed when the window left (`ChatSession.holdTranscript`): records, unread state, approvals and notifications go on in the model, but no row is laid out or mounted for them. `MainWindow` posts `willShow` before it is ordered in or its app unhides; the transcript applies what it held there, and the window lays it out, draws and commits it before it is ordered in, so no stale frame shows. A covered (occluded) window keeps updating: the window server shows it again before the app hears it is visible.
- **Chat layout and scrolling.** The Mac transcript uses an AppKit scroll view and an owned virtualized document (`ChatTranscriptScrollView`), with the existing SwiftUI message views hosted per row. The document owns row frames, cached heights and clip positioning through one layout entry point (`layoutTranscript`), which does nothing unless the clip moved, the controller's positioning inputs changed or something was invalidated. A pass builds and measures every row the presented clip intersects (once, from its root's ideal height without a layout flush, so a row is laid out only at its measured size), places them and restores either the latest output or a message ID plus pixel offset before drawing. Each chat's `ChatScrollPosition` (`ChatSession.scrollPosition`) holds the one positioning intent the document realizes on every layout: the latest output, a message held at a pixel offset (a reopened view, a find, a prepend) until a layout mounts it, or nothing, which leaves the reader's message where it is or follows the bottom while the view does. It turns wheel, key and scrollbar input into giving up that intent, prefetches earlier history near the top, draws the overlay scrollbar (which fades 1.2 s after the last scroll through one pending timer whose deadline each wheel event moves, not a wake-up per event, and whose hidden thumb takes the clip's position only when it shows, so streaming and programmatic movement redraw nothing) and holds the rows while the window is off screen; it computes no row geometry and moves the clip itself only for the arrival glide. The lookahead, a viewport in the direction of travel (up to three while scrolling fast: 0.25 s of travel) and a quarter behind, is built in run-loop turns of its own after the turn that scrolled, within a 3 ms budget (one row); a document that just entered a window (a tab switched to) starts it only after 0.3 s or once the clip moves, so switching through tabs builds only what each one shows. It also measures again a lookahead row whose content changed size after it was measured (asynchronous tool output), so the row has its final height before it enters the clip; while the reader scrolls, a pass does not anchor on a row cut off by the clip's top that still waits for that, so its growth goes above the reader; at rest that row keeps its offset and grows downward (it may be a disclosure the reader just clicked). The representable takes the size SwiftUI proposes (its parent `GeometryReader` always proposes one) instead of AppKit's `fittingSize`, which would build a temporary constraint engine over every hosted row on each layout of the enclosing view. Hosts leaving the lookahead are hidden and kept for a reversal, within 1.5 viewports of total height, 16 hosts and 3 viewports from the clip; a hidden host takes no hits, is no anchor and does not count as mounted (`mountedRows`, which diagnostics and `showsRows` read), and is released after 1.5 s without movement, when its row leaves the transcript or when the width changes. A host keeps its SwiftUI root while its row's `ChatTranscriptRowRevision` (revision IDs and flags of what the row closure captures by value) and the shared context are unchanged; what a row observes updates in place. Offscreen height estimates never position already-visible content independently, and an elastic overscroll past either edge is left for AppKit to return, while rows changing above the reader still correct it. Following settles 22 points above AppKit's own bottom edge, and a followed clip below that offset that AppKit moved within the last 0.5 s (a momentum scroll, or a bounce returning to AppKit's edge) is left alone too, moving only further down for new content; a clip the passes left there, because rows above it measured shorter than their estimates (the lookahead after a chat appears), goes to the follow offset in the same pass, or the text would drop 22 points for a frame or two: pulling it back on each frame fought AppKit's animation, which then never ended and flung the clip far past the document. During AppKit's live scroll (a gesture, its momentum or bounce, between its live-scroll notifications) following does not move the clip at all, even after momentum near the bottom arms it again: AppKit applies its own origin on every frame, so any correction there starts that fight. The live scroll's end lays out once and settles a followed bottom. Short followed arrivals glide (0.22 s, one step per displayed frame); larger bursts pin directly to keep row construction bounded. Content, bounds, scrolling and visibility changes invalidate layout, and every host checks its ideal height after each of its own layouts, so content that grows on its own (formatting arriving, an observed model changing) is measured again without a per-row report; an invalidation made inside the document's own layout (the controller's completion work) still gets its pass. There is no periodic viewport watchdog, lazy-stack rebuild escalation, per-row scroll marker or SwiftUI item scrolling. Removing or prepending rows preserves a retained visible neighbour, and user input cancels pending programmatic positioning. Tool-detail disclosure and per-file source/diff choices live with the transcript, survive host recycling and content revisions, and expire when their rows leave the conversation.
- **Reply placeholder.** A prompt sent from Chat that starts a turn arms it (not a steered message, not with Reduce Motion or in the radio log); once 0.5 s have passed and the agent acknowledged the prompt while still working, the transcript's last row is an empty assistant bubble (`ChatSession.pendingReply`, a row with `placeholder` set). One light moves at a time: from the send the composer's border stays neutral (`replyHaloOwnsActivity`), the bubble shows the footer's activity (◆ and orbit, label, time; `ChatReplyPlaceholderStatus`) where its first word will be, with a stop on hover, while the footer's dims to a still ◆ and label, its time blank in its slot and its details still a click away (`replyShowsStatus`), and the composer's lap goes around its outline (`ChatReplyHaloView`, one overlay above the rows of the transcript document, framed on the bubble's rows). Scrolled out of view (the transcript document reports it from the rows' frames, within its insets, as `ChatSession.replyBubbleInView`), the bubble hands the activity back: the footer is at full strength and the composer's border laps. The new turn's first reply, tool step or narration takes the placeholder's row ID, so it fills the same row without a second entrance; a reasoning summary, its own disclosure row, shows above the placeholder instead. Then the footer's activity comes back to full strength and the light and its accent edge fade into the bubble's outline over 1.2 s (`ChatSession.landedReply`), after which the composer's border fades its working light back in (0.4 s) for the rest of the turn. Content of an earlier turn never takes it over, content before it shows disarms it, and a turn that ends, a failed prompt or a reset removes it.
- **Typed reveal.** A reply that streams into the live turn while its chat shows (Codex's and Pi's deltas, `ChatTypingReveals.streamingAgents`) types out instead of landing in bursts: a per-message clock (`ChatTypingClock`, pure and given its times) keeps the reveal about 0.3 s behind what has arrived, at least 28 characters a second while text waits, eased so its speed never jumps, pausing after `,;:` and `.!?` and at a new block, and catching up faster once the stream ends; a 2-point accent caret follows the last character shown in a text block (solid while typing, blinking while caught up, fading once complete; code, tables and rules show none; a reply whose first words are all a construct still arriving shows the caret alone on a line, never an empty bubble). Claude Code posts whole messages (`ChatTypingReveals.postingAgents`): one that arrives while its chat shows and would type within 2 s (`postedLimit`) types out as if it streamed in at 160 characters a second (`ChatTypingReveal.postedRate`, pauses counted, with the clock's 0.3 s as a head start), through the same clock and caret, even once its turn has ended; a longer one shows at once. A reveal that rested (caught up, faded, past its blink) takes up what arrives next from where it shows, and a transcript held off screen keeps its live turn with its rows, so a reply typing when the window left goes on when it is back. The reveal cuts the rendered text, never the source: what can show is the arrived text up to anything half-arrived (an open code span, emphasis, link (parentheses in its URL balanced) or autolink, a trailing backslash, a task's unfinished box, a trailing line that may still become a list item, heading, fence or table row; `ChatTypingLayout.stableEnd`), code shows by line and tables by row, and the rest of the word being typed (up to 200 characters: paths and URLs too) is laid out undrawn, and unread by VoiceOver, so it never jumps lines; the message grows a line at a time and following the end follows what is shown. Everything else shows at once: complete messages, other turns, history, a reply first drawn when the chat opens mid-stream (it types from there), Claude Code's longer posts, Reduce Motion, and every test run (`ChatTypingReveals.enabled` is off under `DISPATCH_TESTING` and XCTest, though on in an iPhone app XCUITest launches, so recorded waits on a reply's text never depend on display time; the reveal's own tests turn it on and step its clock by hand). The state lives beside the session's view state (`ChatSession.typingReveals`, `MobileChatSession.typing`), never in the model or on disk, and one display link (the main screen's) runs only while a shown reveal types, blinks (at most 6 s, at about 10 frames a second) or fades, and stops with its session: an idle chat runs nothing. A text view rebuilt as it types loses a selection made in the typing block.
- **Delivery.** After async work or reconnect, a submission revalidates its destination. Uncertain delivery is never retried automatically.
- **Held queues live on the host.** A Claude Code or Pi queue is the host's queue store (`helper/core/src/dispatch/store.rs`): one private file per conversation that every helper of the account shares, changed only by checked replaces, so what the host accepted survives the helper and every client sees one queue. Any helper bound to the agent sends the head item once a claim on it lands in the file; a claim whose helper is gone becomes an uncertain item. A helper that exits with sendable items starts the queue drainer (`helper/core/src/drain.rs`), a client of an ordinary helper that keeps those chats open until nothing is left to send. Chat operations are not serialized per session (`ChatOperations.run` starts a task per call, and a helper call can suspend before writing its frame), so requests from separate tasks reach the helper in any order: a row is marked pending when its upload is scheduled and re-checked right before the call, and Stop waits for an upload already on its way (`ChatSession.upload`) so the helper stops what it was just given instead of receiving it after the stop. A reopened chat hears of a stored queue only when it holds something, so a Mac still showing host rows (it was away while the host sent them) reads `queue.list` once the chat's history arrives, and again after any queue change the host refused as `expired` (`refreshHelperQueue`).
- **Terminal input order.** A tab's input to its helper is pipelined: calls go out in typing order without waiting for earlier replies, and input that queues meanwhile joins into one call (`HelperInputQueue`). Nothing overtakes the attach confirmation, a control client on the PTY, or checked keys, and a failure is reported late but never retried. Herdr wheel steps made while one is in flight join into the next `terminals.scroll`.
- **Agent requests.** Chat attaches only after discovery establishes process and conversation ownership. Approvals and question replies belong to a live request and never migrate with presentation state. Losing verification pauses input but keeps history and drafts.
- **Attachments.** A file the user picks (paperclip or ⇧⌘A), drops on the composer or transcript, or pastes (image data, Finder files) is read once, in the app, converted by `ChatAttachmentImage` and uploaded to the conversation's helper (`attachments.put`); messages and queue items name the host copy by path, never the original, so an agent never opens a file in the user's protected folders and an SSH host gets its own copy. Only helpers that accepted the `chat.attachments` hello feature are offered it, and never for commands, side conversations (`/btw` and `/side` refuse a draft with attachments) or queued edits (refused while the draft's uploads run). A photo's GPS, Exif, IPTC and camera metadata never leave the Mac (`ChatAttachmentImage.withoutMetadata`; orientation kept). Uploads in flight are `ChatSession` state only and belong to the draft they were started for, which takes the stored copy wherever the user switched meanwhile; `attachments.put` goes to the host's helper, not the chat's subscription, so a reopened chat does not drop it. The draft keeps what the host stored (with a small JPEG thumbnail); thumbnails read back from a host (`ChatAttachmentThumbnails`, `attachments.read`) stay in memory, and Quick Look reads a private copy in the app's temporary folder, removed when the panel closes, by the next preview, or at quit. A files view's rows dropped on the composer stay text: their quoted host paths. Delivery per agent is in [integrations](integrations.md).
- **Reviews.** The Review tab (internally still `changes`, ids `git-changes-*`) is always a tab of its own. Its line comments are for coding agents: Create review re-reads every commented file, copies the review's text (or sends it to the tab's agent through its composer) and clears the comments, with an in-memory Undo; comments persist per repository (`ReviewRepository`, `reviews.json`) and expire after 30 days unchanged (`ReviewRepository.expiry`).
- **Persistence.** Settings, workspace restoration, saved terminal output, drafts and Review comments belong to `SettingsStore`, `HostSessionStore`, `TerminalHistoryStore`, `ChatDraftRepository`, and `ReviewRepository`; grants, host identities, consent choices and window state also persist in UserDefaults ([stored data](security.md#data-stored-on-your-mac)). Dispatch never restores shell processes. Sensitive files go through `PrivateFile` (owner-only, atomic). Agent histories and tmux/herdr sessions belong to those tools.
- **Pre-release settings.** Only current preference keys are read. Removed sidebar, appearance, contrast, Option-key, prefix-key, multiplexer and dictation settings take today's defaults; they are not translated. Graphite and Lavender are no longer desktop app themes, and an unknown theme resets only that choice. A missing light terminal scheme uses its own default. Multiplexer launching tabs always close after attachment (tests may retain them in memory); `closeLaunching` is no longer persisted. The current clipboard and SSH-consent storage keys stay unchanged so explicit permission choices survive. Reviews and credential protection retain their data migrations.
- **Diagnostics.** `ChatViewportTrace` is opt-in, bounded, and never records conversation text, host/user details, paths, or original row IDs.
- **Chat composers.** The main, `/btw`, and `/side` composers (and the Review tab's comment editors) use `ChatCaretTextView`/`ChatEditorTextView`. Never revert one to a SwiftUI `TextField`: its native caret rendering made Chat slow on 120 Hz Adaptive-refresh displays (external displays and ProMotion MacBooks, especially in full screen). `ChatSideComposerTests` guards caret, IME, focus, and drafts.
- **Composer keys.** Return sends in compact mode; Option-Return and Shift-Return insert a newline without changing editor mode. Command-Return and Control-Return send from either mode. Command-Option-Return takes the alternate send action: steer by default, or queue when Settings makes ordinary send steer. Holding Command and Option together shows that alternate action on the send button and clicking performs it. For a selected or hovered queued message with an empty compact draft, Command-Option-Return sends that row now; Option-Return still inserts a newline. Editor mode (Command-E or a multiline paste) makes Return insert newlines, except a one-line agent command still submits. Escape first dismisses editor mode or clears a queue selection/edit; stopping the agent requires two presses within a second. The Stop button stops immediately. Double Control-D in an empty compact draft closes the tab and quits the agent, or shows Terminal while it works. Both keyboard behaviors are fixed; their removed saved settings are ignored.
- **Engine.** The terminal is the Swift terminal (`Vendor/Term`, ported from Ghostty) behind [`TerminalBackend`](../Dispatch/Terminal/TerminalBackend.swift). It reads a Ghostty-syntax config, bundles Ghostty's shell integration and themes (`Vendor/Term/Resources`), and draws with the contrast shader in [`Shaders.swift`](../Vendor/Term/Sources/TermApple/Shaders.swift).
- **Shutdown.** Save the remote workspace, unmount native views, stop coordinators, destroy surfaces, release the terminal engine, then await SSH/launcher cleanup.
- **Quit runs in two passes.** After `applicationShouldTerminate` answers `.terminateLater`, AppKit waits in a nested event loop that runs no `DispatchQueue.main.async` work and no main-actor task continuations (timers in `.common` modes and posted events do run), so a reply that depends on main-actor work never comes. A user's quit therefore answers `.terminateCancel`, finishes the cleanup on the outer loop and calls `terminate` again, which answers `.terminateNow`; a logout or shutdown (an Apple event with `keyAEQuitReason`) saves the session and is granted at once. Never await main-actor work from inside an AppKit nested loop (modal sessions behave the same).
- **Render threads keep their run loop.** A terminal's render thread (`Frames`) runs its own run loop, kept alive by a port: AppKit invalidates a view's display link when the view leaves its window, and a run loop with no sources left returns, ending the thread and leaving the tab undrawn while its shell keeps running.
- **One state per frame.** A change the user sees lands in one main-actor turn: two layout commits split across turns or tasks, or a pending round trip, let the window draw the state in between, and even one frame of it is a visible flicker. Tests sample state after each changing turn rather than polling for the final state (`TmuxWalkthrough.sidebarShown()`).
- **Animations are scoped.** `.animation(_:value:)` sits on the smallest subtree, keyed to a value that changes only with what it animates: on a container it also animates its children's changes (a font size set in the same update), and an animation around `glassEffect` animates the layout of everything inside the glass. A blanket `.transaction { $0.animation = nil }` kills every animation inside; scope it with `.transaction(value:)`. The model and coordinators use no `withAnimation`, so a `.transition` whose condition flips there runs only if an ancestor's `.animation(value:)` or the transition's own `.animation(…)` covers it, and a child inserted together with its parent never runs its own.
- **Typography.** Every text font draws at Source Code Pro's lowercase height at its size: the median outline height of "acemnorsuvwxz", measured at run time by [`TerminalFontScale`](../Dispatch/Terminal/TerminalFontScale.swift) for terminal fonts, chat's faces (`ChatFont.sizeScale`) and the interface's San Francisco (`AppFont.systemScale`, SF Rounded); `PlanOneTests` holds them to it and `swift scripts/measure-fonts.swift [size]` prints every role. Lines too: from macOS 26 chat's prose (`ChatTypography.lineHeight(for:)`, TextKit's fixed line height) and interface text (`.font(typography, .role)`, SwiftUI's `lineHeight`) are set on Source Code Pro's line at their size (`AppFont.lineHeight`), so switching fonts moves no line or row; that line height is an environment value, so window, pane and sidebar roots set a plain font and leave it to the views that set a role. Widths stay each face's design: text that changes in place reserves its widest variant (`ReservedText`), and SF Symbols beside text take its role's size (`AppTypography.symbol`). Sizes are offsets from Settings' font size: terminal and code at it, chat prose one point over, interface text in `AppTypography.Role` (title +0.5, label −0.5, body −1.5, caption −2.5, micro −3; only display headings pick their own). Settings draws at a fixed 13.5, so its controls stay put while the slider moves. The interface font is San Francisco by default; text that is code (paths, commands, color values) stays Source Code Pro (`AppFont.code`). Activity marks are SF Symbols (`ActivityMark`), never characters: San Francisco lacks ◌ ◆ ◐ and would take them from mismatched fallback fonts.
