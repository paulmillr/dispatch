# Native integrations

Rules every integration follows: server jobs and agent processes belong to their servers and agents; Dispatch only presents them. Detaching, closing, quitting, forgetting a host, and resetting permissions never kill remote work. Reconnect and retry never create replacement jobs, replay commands, or resend input whose delivery is uncertain.

## tmux and herdr

Launch with `tmux -CC new-session -A -s work`, or `herdr` (`--session NAME`, `session attach NAME`). tmux windows become tabs that keep their server splits; herdr workspaces/tabs become spaces/tabs. A tab moved to another space keeps its splits on both (herdr has no tab move between workspaces: the helper moves its panes one by one as one move, and puts them back if a step fails).

- **Close tab** terminates only if every pane is verified idle (foreground, background, and stopped jobs). Otherwise, or if inspection is unavailable (e.g. disconnected), it detaches. Close space, Detach, and quit always detach.
- **Double Ctrl+D in Mac Chat** with an empty draft and an idle agent removes its tab and selects its neighbor immediately. The terminal and chat connection stay alive while `/quit` finishes; then the terminal closes under the usual idle-job policy. A refused quit, a lost connection, or an exit still unconfirmed 6 seconds after delivery restores the tab and reports the failure, without retrying. Busy agents and agents without `/quit` still switch to Terminal. The shortcut is fixed; the removed setting no longer changes it.
- **Quit and local shells.** When the local helper ends, its shells get a hangup and up to 0.7 s to finish their exit work (zsh writing its history under its lock file) before any still running is killed. Killing at once left `~/.zhistory.LOCK` behind, and the next zsh waited 10 s for it.
- A client without a shell of its own (the iPhone app) creates a space with `backends.create`: for tmux it starts the server with one detached session when none is running. Opening (`backends.open`, every reconnect) never starts one.
- **Typing and scrolling** in a tmux or herdr tab do not wait for the helper's replies. Each tab's input goes out in typing order as soon as the call before it is on the wire (`HelperInputQueue`), after the attach is confirmed and no control client holds the PTY; input typed meanwhile, or while the calls on the wire hold 256 KiB or number 64, joins into one `terminals.input`. Checked keys (`terminals.keys`) never join and wait for every earlier reply. Wheel steps made while a `terminals.scroll` is in flight add up per kind (page, modifiers, cell) and go out as one step when it returns. tmux answers `scrollback_app_owned` and scrolls in the renderer as before. Waiting for each reply cost a round trip per key (ten keys took 12.6 s over a 1 s link).
- **Detached** sidebar items reattach to the original client or session, never a replacement. The list lasts only for the current run.
- Layout presets rearrange tabs locally; they never touch server processes or nested splits. Tabs move only between spaces on the same backend connection.
- A successful handoff closes the launching tab, over SSH too. Production always closes it; tests can keep the launching shell through the in-memory `Workspace.closeLaunching` override, which is not a saved preference. The tmux gateway lives while native panes need it, and remote herdr keeps its SSH connection until the last native view detaches. A failed attach leaves the terminal usable.
- Installing (what Dispatch for iPhone's hint shows; Dispatch never installs either): tmux from the system's packages (`brew install tmux`, `sudo apt install tmux`, `sudo dnf install tmux`); herdr as a release binary, e.g. `curl -fL -o ~/.local/bin/herdr https://github.com/herdrdev/herdr/releases/download/v0.9.5/herdr-macos-aarch64 && chmod +x ~/.local/bin/herdr` (`herdr-macos-x86_64`, `herdr-linux-$(uname -m)`).
- **New tmux windows and panes** (Dispatch's New tab, splits, a new space on the server) with nothing to run of their own start what `tmux new-window` would: the server's `default-command`, else a login `default-shell`, as the session's options (else the global ones) name them. Dispatch's integration then reaches them only through variables any shell may inherit (`new-window -e`): the helper's zsh `ZDOTDIR` wrapper files and, on the Mac, the app's wrappers (its zsh `ZDOTDIR`, exported `BASH_FUNC_*` functions, fish's `XDG_DATA_DIRS`) and Ghostty's zsh and fish integration. What only the prepared shell's own start consumes stays out: `SHELL`, `ENV`, `BASH_ENV`, `HISTFILE` and the bash startup and Ghostty injection variables (bash reads them only when started with `--posix`, and a later `sh` would read `ENV`); variables the prepared command removes are set empty, since tmux cannot unset a pane variable. Only when the server would start the very shell the helper prepared (no `default-command`, `default-shell` is that shell) does the pane start the helper's prepared command, with all of its integration (bash's startup through `ENV`, fish's `-C` functions, Ghostty's bash integration on the Mac). A launch (an agent, a program) runs as given whatever the server's defaults. Settings › General › New tabs › Shell applies to plain local tabs only, never to tmux windows. Under a `default-command` or a different `default-shell`, a bash or fish pane on an SSH host therefore has no typed `claude`, `codex`, `pi` and `herdr` functions, and a Mac bash pane no Ghostty prompt integration.
- **Prefix keys** (Settings › Keyboard): a tmux tab answers its server's own prefix table for the tab's session: `prefix` and `prefix2` arm it, `repeat-time` times `-r` bindings, all three as the session's options (else the global ones) set them, and `list-keys -T prefix` gives the bindings. The helper reads it (`backends.prefix`) when the session first shows (a failed read is tried again with the next topologies, three times in all), again after every ended prefix sequence, including Escape and an unbound key (so a `bind` or `set prefix` made meanwhile applies from the next one; tmux tells a control client of no option or key table change, so these are the only refresh points), and after a reattach; until the first answer the tab uses tmux's defaults, and a prefix of `None` turns prefix keys off for that session. A binding becomes a Dispatch action only when it does what tmux would: `new-window` and `split-window` (`-h`/`-v`) with no options but `-c "#{pane_current_path}"` (Dispatch's new windows and splits start there anyway), a bare `kill-pane`/`kill-window` (also behind `confirm-before`), `command-prompt` templates that only rename the window or session or find a window, and the other default bindings; single-reply pane, window and layout commands (`select-pane`, `resize-pane`, `swap-pane`, `select-layout`, `send-prefix`, …) go to the server as they are. A window index (`select-window -t :=N`) selects that server window in the tab's session, whatever `base-index` and gaps make the tab's position; an index with no window beeps. Any other binding (a program, a window name, a size, a target, command lists, tmux's own menus and prompts) is refused with a beep and never replaced by a different action. Control-mode input never passes through tmux's key tables, so root-table (`bind -n`) and custom tables (`switch-client -T`) are not used: those keys go to the terminal.
- **Pane focus** is Dispatch's own: another tmux client selecting a pane does not move the pane a tab shows. tmux ≤ 3.7 keeps a pane per control client (`refresh-client -f active-pane`); tmux 3.8 removed that flag and shares each window's active pane, so the helper remembers the pane Dispatch focused in each window and keeps it when a read caused by others shows another (`Client::chosen`); a read after Dispatch's own change takes tmux's, and a pane that left its window is forgotten. A window Dispatch never focused follows the window's active pane, as tmux 3.7 does.
- Versions: herdr validated on 0.9.5, tmux on 3.7c and 3.8, and their CLI forms pass through. tmux ≥ 3.7 reports bracketed-paste state. Older servers fall back to paste markers, with a Chat warning that readiness can't be verified. Ownership, copy-mode, disabled-input, and synchronized-pane checks still apply.

## SSH

OpenSSH owns host keys, identities, aliases, ports, and jumps. **Remote helper** (Settings › Features, on by default; off is plain SSH) decides whether to upload the helper, and **Auto-confirm uploads** (off by default) whether a new host asks first; Escape or a timeout aborts the `ssh` (status 130) rather than silently falling back to plain SSH. What the helper may read and change is listed in [security](security.md#ssh-integration). Dispatch for iPhone mirrors this per host: its **Helper** switch (on by default) off is plain SSH, and a helper that cannot be installed, started or used falls back to plain SSH with the reason shown, PTY shells only ([Plain SSH](ios.md#plain-ssh)).

- **Helper:** the bundled Rust helper (macOS 14+ on Apple silicon, Linux arm64/x86-64) needs no remote compiler or Python; its contract is in [`helper/PROTOCOL.md`](../helper/PROTOCOL.md). Unsupported hosts fall back to ordinary SSH. Cached legacy C helpers grant nothing.
- **Setup after login:** the typed `ssh` logs in with a command that waits for Dispatch, then the Mac works over the connection's master, one exec channel at a time: (1) the **probe**: one channel that names the host's platform (`uname`), checks the cached helper (folders, owner, mode, size, SHA-256) and starts it with no grant (`--remote --capabilities '' --stdio`), all in one command; the Mac verifies its greeting (version, identity, the consent the grant needs). A cache without the helper says so instead and starts nothing: the helper is uploaded on a channel of its own, then the probe runs again. (2) The **release**, only after that greeting: one `login.release` request on the probe's channel, which writes the ready file the login waits for (the same checks the earlier release script made; when the probe's channel drops first, that script runs once on a channel of its own). The login then checks the named helper itself and runs `<helper> login …`, which starts the session's bus; the user's command runs inside it, once. (3) **`connect`**: a channel to that bus, opened as the release is sent, waiting for the bus; this is the session the app keeps. A warm login costs two exec channels and one request (about 6 round trips after the login's own, down from five channels and 10 to 12), a first one adds the upload's channel and a second probe. A step that fails for a reason another attempt can fix runs once more; any other failure releases the login with its reason and it opens the plain shell, never running the command twice.
- **A home folder that cannot run programs** (mounted `noexec`, or blocked by policy): the helper is installed in and started from `$XDG_RUNTIME_DIR/dispatch/bin/versions/<sha256>/` instead, when that folder is private and the grant has no agent hooks ([security](security.md#ssh-integration)). The helper's own work (tmux and herdr mapping, terminals, stats, files) runs. What runs `~/.dispatch/bin/dispatch-helper` cannot: with the hooks grant, the agent hooks and the typed `claude`, `codex`, `pi` and `herdr` functions the login shell's startup files define (so such a grant falls back to a plain shell, and installing hooks on such a connection fails with that reason); and Chat's New chat, which starts its agent through it. Without a usable runtime folder it falls back as well; the login says why either way.
- **Consent covers the connection opened:** consent resolves the typed invocation (`ssh -G`); the master Dispatch then starts (its own login command, `-tt`) is resolved again, and so is a reconnect's `-f -N` login, because `Match command`, `Match sessiontype` and `Match exec` can resolve them to another host, account, key or proxy. Any difference besides the options Dispatch sets itself keeps the helper off: the login runs plain `ssh` after saying why ("Dispatch SSH integration unavailable (…); opening plain SSH."), and the reconnect stops before logging in, with the reason on its bar (not retried automatically). A reconnect has no plain-SSH fallback: its shell resumes only over a master Dispatch verified, so such a connection is reopened by hand. Each check ignores only the options its own invocation sets (the login: ControlMaster, ControlPath, ControlPersist, `-tt`, the keepalive; a reconnect also `-f -N`, and an automatic one `BatchMode` and `ConnectTimeout`).
- **Grants are per configuration:** executable, destination, account, port, proxy, and identity. Hosts that share a sidebar card (same destination, account, port, proxy route, and host-key alias) share presentation only; each connection keeps its own generation and grant. Conflicting machine identities split the card.
- **Grant changes:** reductions take effect immediately (helper operations, hooks, and native views stop; the shell and jobs stay). Increases apply on the next explicit connection. Helper updates keep existing grants, but new capabilities need a new choice. Reset/Forget/Reset all revoke live grants and clear saved choices without touching remote jobs.
- **Passthrough:** noninteractive commands, RemoteCommand, multiplexing overrides, tunnels, and subsystems run as plain SSH. `ssh -tt host cmd` can be enhanced. Nested interactive SSH stays plain and suppresses outer-host agent discovery. Clones use `ClearAllForwardings=yes`.
- **Session options on Dispatch's channels:** helper channels over the master (`-F /dev/null`, master only, never a fresh login) send the variables the login sent with `SendEnv`, by name, with the values of the terminal `ssh` was typed in, captured when it started (the app's environment is not the terminal's; `DISPATCH_*` stay behind); `SetEnv` comes from the master itself. They never ask for a PTY or agent forwarding. The shell a reconnect resumes sends the same variables and forwards the agent exactly when the connection does (`ForwardAgent`/`-A`).
- **Relative paths:** OpenSSH resolves `-F ./config`, `-i key`, a configuration's relative `IdentityFile`, `ProxyCommand ./script` and `Match exec` from its working directory. Dispatch keeps the local folder `ssh` was typed in with the connection (saved with it) and runs every later ssh for it from there: the reconnect's configuration check and login (sheet or automatic), a new tab's clone, the New space probe and Remove Dispatch. A connection saved before this, or a plain `ssh` Dispatch only observed, has no folder and resolves as before.
- **Shell integration** keeps user aliases and functions, resolves executables through the caller's `PATH` (skipping Dispatch's shims), and never wraps `sudo`.
- **Keepalive:** the SSH master Dispatch starts for a connection (the typed login, a reconnect's login) sends an OpenSSH keepalive every 15 s and gives the link up after 8 unanswered (`ServerAliveInterval=15`, `ServerAliveCountMax=8`): a link that died while idle ends in about two minutes, while a 40 s outage is survived. A connection with its own keepalive keeps it: the options come after yours (OpenSSH uses the first value given), and are left out when `ssh -G` shows an interval from your ssh_config. Channels opened over the master share its connection.
- **Slow connection mode** (Settings › Experimental, off by default): helpers started after the change keep at most 256 KB of terminal output on its way to this Mac and wait for it to be drawn (`terminals.window`, [protocol](../helper/PROTOCOL.md#features)), so a keystroke or a reply never waits behind megabytes parked in SSH and TCP buffers while a terminal floods a slow link. Remote hosts take the setting at their next login or reconnect; local tmux and herdr once Dispatch restarts.
- **Setup on a slow link:** the setup's steps share 60 s, except the helper upload (a first connection, or a new version), which is paced by the link: it fails only when ssh takes none of it for 25 s, and its time does not count against the other steps. The waiting login likewise does not count time while the uploaded file grows (within 30 s of it last growing).
- **Stats** never start or keep an SSH connection. Latency is a `stats.ping` round trip through the helper, not ICMP; one probe runs at a time, with a timeout that never disconnects (a timed-out probe only marks the reading stale). Probes, stats requests and other short requests to a host wait 3 s plus ten of its last measured round trips, at most 30 s (10 s or more before a reading, or after a probe timed out).

### Reconnect

Quit saves remote hosts, layouts, and plain local spaces to `~/Library/Application Support/Dispatch/host-session.json` (unless Settings › General › **On launch** is Start fresh). They reopen disconnected, with no automatic login. Tabs keep their placement, renderer, loaded Chat history, and drafts across transport loss. Recovery re-verifies the SSH configuration (resolved from the folder `ssh` was typed in, together with the reconnect's own `-N` login, [above](#ssh)), grant, account, and host identity over a fresh connection; the shell it resumes keeps the connection's SendEnv variables and requested agent forwarding. tmux/herdr reattach to existing servers and panes only, and a missing session stays an error. Chat rejects reads and input from the old connection, and queues stay paused. Direct `/usr/bin/ssh` and plain-SSH connections get no managed recovery. Recovery state does not survive an app restart.

**Reconnect automatically** (Settings › Features › Remote helper, off by default) recovers a connection that dropped while Dispatch was running:

- It starts only after the launcher reports a transport loss with no exit status or receipt, never after Disconnect, a normal exit, or a launch restore.
- Attempts run the same verified recovery but show nothing: the remembered grant only, and OpenSSH with `BatchMode=yes` (keys and the agent).
- An unreachable host is retried 2 s, 4 s… up to a minute apart, and at once on wake or a network change. So is a login whose later steps did not finish in time (a slow link): the helper setup timed out or failed in a way another attempt can fix, the replacement shell did not start, or its retained spaces did not restore (they get 30 s plus 30 of the host's last measured round trips, at most 120 s; 60 s without a reading).
- Retries for that drop end, leaving the Reconnect bar, when OpenSSH refuses the login (a password, passphrase, or changed host key), a later recovery step fails for another reason (a changed host, account, grant or launcher, a setup that cannot work on that host), the login tab is closed (herdr's after handoff, whose recovery opens a login tab), or you choose Reconnect, Cancel, or Disconnect.

## Chat

Codex, Claude Code, and Pi attach to the agent already running in a local terminal, tmux/herdr pane, or SSH session (remote discovery needs the Chat transcripts grant on that connection, included when enabling the helper). Terminal and Chat share that process. A verified conversation opens Chat in its tab unless the user chose a view there or Settings › Features › Chat mode › Open agents in is Terminal (no launch cover then either); the tab's Chat switch shows it.

- **Ownership:** discovery must verify both the process and the conversation. A matching directory, inherited tmux environment, or coincidental PID proves nothing. Ambiguity (e.g. multiple main Codex rollouts) pauses input but keeps the transcript and draft. Codex guardian reviews and subagents are excluded. A direct registered SSH connection outranks its enclosing pane.
- **Transcript:** a re-read of the same transcript file (a reopen, a read that raced a write, an attribute change) adds only records the chat lacks; a chat's history is replaced only when its file was replaced or shortened, or for another branch (Pi's tree). The app merges a replacement that shares records with the shown turns, removing only the turns and records the page proves gone (another Pi branch keeps its shared ancestors), so remaining rows, expanded groups and the reading position stay. A conversation continued under a new id keeps its rows. Request-log lines (Claude's `api-request*`) don't count toward a page. Multiplexers announce `agent.changed` only for another harness, session, transcript or process.
- **Hidden terminal:** while a chat tab shows its transcript, the terminal of a tmux or herdr chat on a helper with `terminals.follow` is not streamed to the Mac (the helper holds its output for that tab alone); showing the terminal again restores its screen from the host before new output. The Mac counts a chat tab's terminal as hidden while its view is not on screen: the tab is not shown in its pane (another tab, an unselected space), the session shows its transcript or files, or the window is minimized or fully covered. It holds the output only after 2 s hidden (`HelperWorkspace.followGrace`), so a glance at the transcript costs no repaint, and follows again as soon as the terminal shows or the Mac reads its screen itself (Chat adopting text typed into Claude's prompt: held again 2 s after the last such read); the repaint is ordinary output for the renderer (tmux rewrites the whole history after `\ec`, so scrollback is complete again; herdr redraws the alternate screen, without scrollback). Only tabs whose session has an agent bound are held, only on a helper that also accepted `screens.host` (the prompt watcher then reads the host, not this app's screen); a tab whose agent exits follows again at once, and plain terminal tabs, native terminals and helpers without the feature always follow.
- **Input:** destinations are revalidated before paste and Return, and uncertain delivery pauses for review instead of retrying. Text already in an agent's native editor blocks submission. In a plain terminal (the helper's own PTY), a key typed for an agent right after a paste waits until the agent has read the paste and one poll more (polled every 10 ms, at most 5 s, the ownership check run again before each try), so an agent that exits at the end of a paste leaves no Return for the shell that resumes. Multiline text starting with `/` or `!` stays literal. Only an explicit user action switches to Terminal. A bare `/resume` is one: once Claude Code or Codex has it, Chat switches to Terminal for the agent's session picker and follows the conversation picked there.
- **Approvals and questions** are bound to the live request, process, and conversation. They never migrate, replay, or let one approval cover a later request. Main-session Codex approvals and Claude approvals/questions need Dispatch's agent hooks (installed as described in [security](security.md#agent-chat)); agents must restart to load them, and remote hooks also need the hooks grant and a home folder that can run programs (`~/.dispatch/bin/dispatch-helper`). Codex questions and side-conversation approvals use native App Server requests and events.
- **Queue:** messages keep their send order and their conversation/process binding. Delivery waits for Terminal view, menus, questions, approvals, history loading, and open side sheets. Stop pauses the queue until Resume. When the native queue API exists (Codex locally, or `agent.queue` over SSH), Chat mirrors Codex's own queue instead, and an accepted entry never falls back to terminal input.
- **Subagents:** while an agent's subagents run (SubagentStart until SubagentStop hooks; background agents outlive their turn), the composer shows their count, and the count opens one row per agent, oldest first: its task (Claude's `agent-<id>.meta.json` description, else its type), its type, how long it has run since SubagentStart (the host's clock; for Codex, from when the app first saw it), and for Claude its tokens (input, output and cache creation, each model call once, from `agent-<id>.jsonl` beside the session's transcript). Token counts reach the app at most once a second; the clocks tick in the app while the list shows. The working line names their types while the agent waits on them. Details in `helper/PROTOCOL.md` (`State.agents`).
- **Background shells (Claude Code):** while Claude runs shells in the background (Bash `run_in_background`, or a command it sent there when it outran its timeout), the Mac's composer shows their count beside the subagents', and the count opens one row per shell, oldest first: what Claude said it does (else its command), its command, and how long it has run since its call. They read from the transcript only (the Bash result names the task, its task notification ends it) and do not keep the working line or its clock: a server can run for hours while Claude waits for input. A conversation resumed in a new Claude process drops the shells of the old one. The iPhone shows them as a line over its composer that opens the same list in a sheet. Details in `helper/PROTOCOL.md` (`State.shells`).
- **Side conversations:** `/btw` is a read-only fork and `/side` a full-permission fork, for local/remote Codex and local Claude. Their replies stay out of the parent transcript, and closing the sheet ends the child process. Dispatch for iPhone offers them wherever its helper lists the command, on a pushed screen ([ios](ios.md)), and ending one there ends the child process too.
  - A fork runs on the parent's provider and model, with the credentials the parent's configuration names ([security](security.md#agent-chat) lists which variables and why). Codex: the child `app-server` gets the parent's `-c`/`--config`, `--enable` and `--disable` options (not the permission keys: `approval_policy`, `sandbox_mode`, `sandbox_workspace_write`, … stay the configuration's, so `/side` keeps Dispatch's approvals), reads the parent thread's model, provider and effort (`thread/read`) and forks on them; when its configuration names variables it was not given (a provider's `env_key`, header or MCP credentials), the parent's values are read and the child is started again with them. A fork Codex reports on another model or provider fails instead of answering, as does a side of a Codex whose `thread/read` does not report the thread's model and provider (side conversations were verified with Codex 0.164). The model picker's catalog server gets the same overrides and the credentials its default provider names. Claude: the child runs on the parent's current model, with the variables Claude's credential commands (`apiKeyHelper` and the cloud refresh helpers) name in its settings.
  - Not carried over: the parent's `/side` permissions given on its command line (`-s`, `-a`, `--dangerously-bypass-approvals-and-sandbox`, or the permission keys of `-c`) or changed while it runs (the child uses its configuration's), Codex's service tier, and Claude's own command-line options (`--settings`, `--mcp-config`, `--permission-mode`). `DISPATCH_SIDE_ENVIRONMENT` in the agent's environment names further variables to pass on ([security](security.md#agent-chat)).
  - A Codex started with `--profile` (or `-c profile=…`) has no side conversations: its child `app-server` cannot load the profile, so it might run on another provider; the side sheet says so. Its model picker lists the models of the configuration without the profile.

### Per agent

- **Codex hooks:** installs only `PermissionRequest`, `SubagentStart`, and `SubagentStop`. Process exit, a verified change of conversation or process, and native `thread/closed` clear running subagents; an ordinary turn ending or transcript refresh does not. Compaction status comes only from the App Server's `contextCompaction` items, so sessions without an App Server connection have no live compaction indicator. Discovery audits existing installations without editing them; explicitly enabling the integration appends any missing Dispatch hooks while preserving existing handlers.
- **Codex:** local launches through shell integration use a private App Server with the native TUI. Chat follows the main thread across `/new` and `/resume` and ignores ephemeral threads. Explicit `--remote` endpoints keep their own server. Sessions that bypass shell integration, older CLIs, and unsupported flags stay Terminal-only. A profile (`-p`/`--profile`) is one: the private server cannot load it, so such a TUI runs with `--no-daemon` and the launcher prints why before the TUI starts ("dispatch: codex --profile runs without Dispatch's private app server …"): Chat works through the terminal (no native queue or live diffs) and `/btw` and `/side` are unavailable. The same settings given as `-c key=value` keep the private server. Live diffs need an accessible App Server (Unix socket, the helper channel, or an unauthenticated local WebSocket), and partial diffs need Codex's `features.apply_patch_streaming_events`. Dispatch never enables experimental flags.
- **Claude Code:** adds `PermissionRequest`, an `AskUserQuestion`-only `PreToolUse` hook, and the lifecycle hooks `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PostToolUse`, `SubagentStart`, `SubagentStop`, and `Stop`. An approval-only installation from an older build is incomplete; enable the integration again to install the current hooks. Launch discovery does not upgrade it automatically. Questions expire after 180 s; Skip denies them. Disabling hooks returns requests to the native UI without approving them. Stop sends one Escape after verifying the working conversation; it must never open the rewind menu.
  - **Model and effort.** A switch made in the terminal reaches the transcript only as Claude's own command output ("Set model to \`Sonnet 5.5\` for this session only", "… and saved as your default for new sessions", "Set effort level to high (this session only): …"; an Escape out of `/model` writes "Kept model as …"), which the helper reads (`helper/harnesses/claude/src/history.rs`). A model switch without an effort suffix can still change the effort silently; only the live footer shows it. In `/model`, `s` applies a choice for the session and Enter saves it as the default, so the helper's menu walk never presses Enter on a probe. It resolves a requested model by row name, a unique row named by the id, or a unique non-default row describing it (`menu.rs` `listed`); a walk that cannot finish sends Escape rather than leaving the menu open. The iPhone's New tab and New chat start on Claude's own default, set with its `/model`; the phone remembers no model or effort of its own (`ChatModelMemory` keeps only the last agent and the menus seen).
- **Pi:** needs the **Pi chat extension** setting, then `/reload`. Chat requires the bundled `extension-v2` event channel; an older extension can be discovered but chat operations fail with an instruction to update the extension and run `/reload`. There is no polling fallback. Chat follows the current branch of the session tree. `--no-session`, print, and RPC processes don't attach. Remote installs resolve `PI_CODING_AGENT_DIR` and touch only Dispatch's extension.

### Attachments

Images and files attached in Chat (button, drop, paste) are read by the app in its own process (images without their location and camera metadata, [security](security.md)) and uploaded to the helper on the agent's host (`attachments.put`, feature `chat.attachments`, [protocol](../helper/PROTOCOL.md#attachments)). The helper keeps a private copy under `~/.dispatch/attachments/` (its file name reduced to letters, digits, `.`, `_` and `-`; the app shows the original name) and the message names that copy, so the agent never opens the user's original and an SSH host gets the bytes, not a Mac path. A copy stays for a day, so an agent may read it again later in its turn, and as long as a queued message names it. Commands and side conversations take no attachments.

- **Claude Code:** each image path is pasted on its own; Claude Code 2.1.302 reads a pasted path ending in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` and shows `[Image #n]`. The helper waits for each placeholder (a few seconds: Claude reads and may scale the file first) before the next paste, then pastes the text and presses Return. A path Claude keeps as text (it read no image there) stays in the message as that image's path and is not pasted again; an image that shows nothing in time goes as a path line instead; anything else in the composer fails the send before Return, so nothing is sent twice. The transcript keeps only the image data (and Claude's own `[Image: source: …]` companion line), so the helper remembers which copies each send delivered, and when it started, to name them in history.
- **Codex:** the main TUI gets each image path pasted on its own (Codex 0.163 shows `[Image #n]`; a path with spaces is single-quoted, since a raw one stays text), then the text and Return. Native input (side threads, the native queue, a queued steer) carries `localImage` items. Rollouts keep the paths (`local_image`), so history names them directly.
- **Pi:** the text fallback for images too: Pi opens the stored copy with its read tool, which reads images. (Pasting a path into Pi's own editor does not attach it, and sending image content through the bridge would change the bundled extension.)
- **Every non-image file:** the **text fallback**, the message text, an empty line, and one path per line (only the paths without text). The agent reads them with its own tools. A text that starts like a command is fenced for Claude Code and the Codex TUI as always; the path lines follow the fence, and paths alone are never fenced (both agents take `/a/b` as a message).
- **History** shows the text as typed and the attachments as thumbnails or file chips: placeholders, and paths under the host's attachments folder before the text or as lines after it, are removed from the text. Only an app that asked for attachments gets this; an older one gets the records exactly as before (an `[Image]` line per image). On another device the thumbnails come from the host's copy (`attachments.read`) while it lasts; after that a placeholder.
